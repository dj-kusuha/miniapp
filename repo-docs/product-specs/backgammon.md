# Backgammon

## Summary

ブラウザだけで遊べるバックギャモン。対戦相手は、勝敗のみを報酬に自己対局で
学習したニューラルネット AI（TD-Gammon 方式）。

**AI とルールエンジンは外部リポジトリ
[dj-kusuha/backgammon_engine](https://github.com/dj-kusuha/backgammon_engine)
で開発している。** ただし english-typing と違い、**そちらは Python で
サーバ実行前提**なので、成果物をそのまま置けない。**JavaScript へ移植した
ものを `docs/backgammon/` に配置する。**

## Users

- バックギャモンを指したい人（ルールを知っている前提）
- 学習した AI がどのくらい打てるのか触って確かめたい人

## Problem

engine 側にも Web フロントエンド（`play_web.py`）はあるが、**Python サーバが
必要**でローカルでしか動かない。URL を開くだけで遊べる場所が無い。

## Goals

- URL を開くだけで、インストールもサーバも無しに 1 局遊べる
- AI は engine の同梱モデル（`models/td_gammon.json`）と**同じ手を選ぶ**
- ルール（合法手生成・ベアオフ・バー・ギャモン / バックギャモン判定）が
  engine と一致する

## Non-Goals

- ~~**ダブリングキューブ**~~（初版では扱わなかったが、その後に実装した。
  設定で使う / 使わないを選べ、ジャコビールールも切り替えられる）
- **4-ply 以上の先読み**（3-ply のさらに約 100 倍）
- 対人戦・通信対戦・棋譜の保存・アカウント
- 盤面の反転表示（engine 側の既知の制約と同じく White 視点固定で始める）

## マッチプレイ（2026-08-22）

**アンリミテッド（マネーゲーム）とポイントマッチを設定画面で選べる。**
ポイントマッチは 1〜7 ポイント。

| | アンリミテッド | ポイントマッチ |
| --- | --- | --- |
| 終わり方 | 終わらない（通算だけ数える） | 先に N 点取った方の勝ち |
| ジャコビー | 選べる | **常に切る**（マッチには無いルール） |
| クロフォード | 無い | **あり** |

進行は `src/match.js` の `Match` が持つ。**engine（Python）側にマッチプレイは
無い**ので、ここが正本でパリティの相手はいない。

### クロフォードルール

**片方がマッチポイント（あと 1 点）に達した直後の 1 局はキューブ禁止。**
その 1 局が終われば、以降（ポストクロフォード）は再びダブルできる。

- **クロフォード局を経ずに終わるマッチはある。** 0-0 からギャモンやキューブで
  一気に取り切ると、誰もマッチポイントを通らない。「必ず 1 回来る」ではなく
  **「多くても 1 回」**が正しい
- **1 ポイントマッチは最初の 1 局がそのままクロフォード局**になる（開始時点で
  両者ともマッチポイントのため）。結果としてキューブを一度も使えないが、
  1 点しか動かないので規則どおり
- 判定は `Game` に `crawford` を渡して `canDouble()` を殺す形。UI 側で
  ボタンを隠すだけにしない

### スコア

**必要点を超えて勝つことはある**（キューブが伸びた局）。棋譜には素の点を書き、
**スコアだけマッチの長さで頭打ち**にする。gnubg も同じ（`5 point match` に
`Wins 8 points` が出る）。

### マッチのキューブ判断は MET で行う（2026-08-22）

**マッチでは equity（1 局あたりの期待得点）が使えない。** 同じ 1 点でも
スコアによって価値が違うため、**マッチに勝つ確率（MWC）**へ換算し直す。
そのための表がマッチエクイティ表（MET）。

- 表は **Kazaross XG2**（25 ポイントまで）。`docs/backgammon/src/met-table.js`
  は生成物で、`tools/build-met.mjs` が作る。**ライセンスと出どころは
  [THIRD-PARTY-NOTICES.md](../../THIRD-PARTY-NOTICES.md)**
- 引き当ては `src/met.js` の `matchWinChance(awayUs, awayThem, crawfordPlayed)`
- 判断は「3 つの MWC を比べる」だけ:

```
ダブルしない = Σ P(結果) × MWC(その結果のスコア)          キューブそのまま
テイクされる = 同上、キューブ 2 倍で
ドロップされる = MWC(いまのキューブ値ぶん取ったスコア)

ダブルの価値 = min(テイクされる, ドロップされる)    ← 相手が選ぶので悪い方
ダブルすべき = ダブルの価値 > ダブルしない
テイクすべき = テイクされる < ドロップされる        ← 提案者の勝率が低い方
```

**場合分けを 1 つも書いていないのに、既知の性質が自然に出る**（テストで確認）:

| 場面 | 出てくる答え |
| --- | --- |
| 自分がマッチポイント（キューブが死ぬ） | ダブルしない |
| キューブが既に必要点に届いている | ダブルしない |
| ポストクロフォードの 2-away | 即ダブル |
| **ポストクロフォードの 2-away でギャモンが濃い** | **打ち続ける**（下記） |
| 2-away 同士のキューブ 2 | ギャモンに価値が付かない |

> **ポストクロフォードの 2-away は「必ず即ダブル」ではない。** 2-away では
> ダブルしなくてもギャモンでマッチが終わる（1×2 = 2 点）のに対し、ダブルすると
> リード側はドロップでき、こちらの取り分は 1 点（＝ 1-away 同士の 50%）で
> 頭打ちになる。実測で P(win) 0.85 / P(gammon) 0.45 の局面では
> **打ち続け 0.650 対 ダブル 0.500** と差が付いた。

### 残っている限界

- **キューブが以後動かない前提（死んだキューブ）で数えている。** テイクした側が
  振り直せる価値を数えていないので、テイク側をわずかに低く見積もる。同じ近似は
  アンリミテッド側（`cubeOwnership = 0`）でも使っており、方針は揃えてある
- **キューブ判断は 0-ply のまま**（着手は 2-ply / 3-ply）
- **マッチのキューブ判断を採点する物差しがまだ無い。** アンリミテッドには
  backgammon_engine のキューブ・ベンチマークがあるが、マッチスコアつきの
  正解集合は作っていない。**「よくなった」と数値で言える段階ではない**
- **アンリミテッド側は従来のまま**（`double_point` / `cube_ownership` の定数）。
  自己対局の観察では、マネーは 80 回のダブルのうちテイクされたのが 6 回
  （92% がドロップ）なのに対し、マッチは 97% がテイクされる。
  [ADR-0017](https://github.com/dj-kusuha/backgammon_engine/blob/main/docs/adr/0017-cube-measurement.md)
  が「ダブルが早すぎるかテイクが渋すぎる」と書いた症状はマネー側に残っている

## Core Flow

1. トップで形式（アンリミテッド / ポイントマッチ）と AI の強さ
   （**初心者 / カジュアル / 中級 / 上級 / エキスパート** の 5 段。既定は中級）を選んで開始
   （**人間は常に White**。盤は White 視点固定なので、色を選ばせると盤が
   読みにくくなる）
2. サイコロを振る → 動かす駒をクリックして着手（出目は左から順に使う）
3. AI が応手 → 決着まで繰り返す
4. 勝敗（シングル / ギャモン / バックギャモン）を表示して、もう 1 局へ

## UI Notes

- モバイルファースト。360px 幅で盤面が破綻しないこと
- 操作はクリック。駒をクリックすると出目キューの手前（左）の目を即座に使って
  動かし、次に動かせる駒をハイライトする（移動先を別途クリックさせない）。
  ドラッグ&ドロップにしない
- 盤は実物に寄せる。ポイントは三角形、バーは中央に幅を持たせ、右端に
  ベアオフ用のトレイを置く（黒は上段側、白は下段側）
- **ダブリングキューブは、ベアオフトレイの反対側（盤の左端）に置く。**
  持ち主がいなければ中央、持ち主がいればその側（White は下 / Black は上）。
  **センターのときの数字は 64**（実物のキューブに 1 の面が無く、まだ回って
  いない状態を 64 の面で表すのに合わせる）。回ったあとは今の値を出す。
  キューブを使わない設定なら中身は空にするが、**列そのものは残す**
  （消すと盤の横幅が対局ごとに変わってしまう）
- **ダブルの返事待ちの間だけは、左端の置き場から外して盤に「打った」形で出す。**
  出す側はダイスと同じ半分（自分は右 / AI は左）で、数字は**提案後の値**
  （＝いまの倍）。返事がついたら置き場へ戻る
- 駒 5 個を積んでも中央の帯を越えないよう、盤は実物より縦長にしてある
- サイコロは中央の帯に置く。自分は右半分、AI は左半分（相手から見て右）。
  **手番中の側だけ表示し、使い切ったら片付ける**
- 出目をクリックすると使う順番を入れ替えられる（ゾロ目のときは無効）
- 「サイコロを振る」は自分のダイスと同じ位置（盤の右半分中央）に出す。
  操作する場所を 1 箇所にまとめる。「もう一局」などは盤の下のまま
- 「ダブル」も盤の中央の帯に出す（**左半分**）。どちらもロール前にしか出ない
  ので、ダイスと場所を取り合わない。**色は「振る」の緑と変える**
  （`--cube-action`）。並んで出るので、同じ色だと取り違える
- AI の着手は 1 手ずつ間を置いて見せる。ダンス（動かせない出目）のときも
  出目を見せる時間を必ず取る。「気づいたら自分の番」になるのを避ける
- **その間合いはスライダーで 0.1〜2.0 秒に変えられる**（既定 1.0 秒。
  0.1 刻み）。置き場所は棋譜の上で、**対局中でもいつでも動かせる**。
  変えた値は次の待ちから効く
- ダブリングキューブを「使わない」にしたら、**ジャコビールールの項目ごと
  隠す**。キューブが無ければ選ぶ意味がないため
- **自分の手番では「ヒント」で最善手を出せる**（下記）
- 棋譜は PC 幅では盤の右、狭い画面では盤の下に折りたたむ
- **棋譜にはキューブの出来事（ダブル / テイク / パス）も残す**。画面の一覧と
  `.mat` の両方。値がどこで動いたか分からないと着手の意味が追えない
- `.mat` は**ファイルとしてダウンロードできる**（`backgammon-5pt-20260823-1930.mat`
  のように形式と日時を名前に入れる）。gnubg へは結局ファイルで渡すので、
  クリップボード経由より短い
- `.mat` の欄は**フォーカスできる**（`tabindex="0"`）。クリックしてから
  **Ctrl+A でその欄だけを全選択**できる。素のままだとページ全体が選択されて
  棋譜だけ取り出せない。**そのためコピーボタンは置かない**

## Technical Notes

### スタック

- 素の HTML / CSS / JavaScript（[FRONTEND.md](../../FRONTEND.md) の
  「単一ページで完結するなら素の JS を優先」に従う）
- **外部 API なし。** すべてブラウザ内で完結する

### AI の推論

同梱モデルは **198 → 128 → 32 → 16 → 5 の MLP**（SiLU・約 633KB の JSON。
2026-08-28 に 128-64-32 から差し替え）。推論は**行列積とシグモイド**だけで
済むので、依存なしで書ける。

```
入力 198 次元 → 隠れ 128 → 32 → 16（SiLU）→ 出力 5（sigmoid）
出力は [勝ち, ギャモン勝ち, バックギャモン勝ち, ギャモン負け, バックギャモン負け]
着手は equity = 2·P(win) + P(wg) + P(wbg) − P(lg) − P(lbg) − 1 が最大の手を選ぶ
```

**細くしたのは 3-ply を軽くするため。** engine の 32,000 局面で
128-64-32 と**強さは同等**（標準 +0.072・ナック +0.004。どちらも有意差なし）
のまま、**第 2 層以降を削って 3-ply を 1.46 倍速く**した。
第 1 層は入力が疎なので広くても安く、**削るなら第 2 層から**
（engine の ADR-0016 / ADR-0025）。

**3-ply まで入れる**（2026-08-21）。強さは engine 側の固定ベンチマーク
（32,000 局面。小さいほど良い）:

| 先読み | 強さ | 1 手あたり（このブラウザ環境） |
| --- | --- | --- |
| 0-ply | 15.6 mEMG | 0.1 ms |
| 2-ply | 9.8 mEMG | 22 ms |
| **3-ply** | **6.6 mEMG** | **中央値 0.8 秒 / 最悪 3.3 秒** |

初版の見積りでは 3-ply は「1 手 5.6 秒で重すぎる」として Non-Goal に
していたが、**推論を 3.4 倍にして実用圏に入った**（下記）。

### ベアオフの厳密解（2026-08-28）

両者の駒が自陣に入りきると、局面は**互いに干渉しない 2 つの競走**に分解する。
相手を打つことも塞ぐこともできないので、「自分が上がりきるまでに何回振るか」の
分布さえ分かれば**勝率が厳密に計算できる**。6 ポイント・15 枚の全 54,264 状態を
engine が先に計算して配っている（`src/bearoff-6x15.bin`）。

| | |
| --- | --- |
| ファイル | 3.9 MB（**Pages の gzip で転送は約 1 MB**）。モデルと一緒に読む |
| 効果 | engine の 32,000 局面で **-0.159 mEMG**（3.235 → 3.076） |
| 内訳 | 適用範囲は 11.8% だが、**着手が変わるのは 1.6%**。その局面の損失が **11.77 → 1.64 mEMG** |

**ベアオフのほとんどはネットも正解を選べていて、残り 1.6% で盛大に
間違えていた**——そこが消える。

- **float16 のまま持ち、引くときだけ変換する**（`Float16Array` は使える環境が
  限られる。1 回の問い合わせで触るのは 2 状態ぶんだけ）
- **読めなくても対局はできる**（ネットの推定に落ちるだけ）
- **厳密さには条件が付く。** 分布は「上がりきるまでの期待回数を最小化する
  打ち方」のもとで計算されており、勝率を最大化する打ち方とは厳密には別物
  （片側 DB の宿命で gnubg も同じ）

### 弱い相手の作り方（2026-08-22）

**先読み 0 が床なので、それより弱くするには別の軸が要る。** モデルが強くなる
たびに最弱の段も勝手に格上げされ、実測で**先読みなしでも gnubg 判定
Advanced / Intermediate**（12.8 mEMG）まで来ていた。

採ったのは gnubg が Beginner / Casual を作るのと同じ**評価値へのノイズ**。
equity に平均 0・標準偏差 σ のノイズを足してから最大を選ぶ。

**なぜこれが人間らしいか: 間違える確率が「判断の難しさ」に自動で連動する。**
equity 差 0.3 の明らかな手は σ=0.05 ではまず逆転せず、差 0.02 の際どい手は
しょっちゅう逆転する。弱い人が「簡単な手は外さず、際どい判断だけ落とす」のと
同じ形になる。

採らなかった案:

| やり方 | 何が起きるか |
| --- | --- |
| ランダムに選ぶ | equity 差を見ていないので、明らかな悪手を平気で打つ |
| 上位 k 手から等確率 | 差の大きさを見ていない。まともな手が 2 つしかない局面で破綻 |
| X% の確率でランダム手 | **間違いが難易度と無相関**になる。ふだん完璧で突然おかしい＝人間味の逆 |

**つまみは 2 つ。** ノイズは正規分布で裾が無限に伸びるので、
**最善から `maxLoss` 以上劣る手は候補から外してから**ノイズを掛ける。

- `noise`（σ）… 際どい判断をどれだけ取り違えるか＝**間違える頻度**
- `maxLoss` … 最善からどれだけ落ちてよいか＝**間違いの深さの上限**

「よく間違えるが、絶対にアホなことはしない」を作るのに両方が要る。

> **ノイズは局面から決定的に作る**（盤面の鍵を FNV-1a でハッシュ →
> Box-Muller）。毎回乱数を引くと、1 手戻してやり直すたびに AI の手が変わり、
> 「考え直した」ように見える。同じ局面は何度でも同じ読み違えをするのが正しい。

> **キューブ判断にも同じノイズを乗せる。** 着手だけ弱くすると「手はヘボいのに
> ダブルは完璧」という妙な相手になる。

#### σ は勘で置かない。gnubg に採点させて決めた

`tools/measure-level.mjs` が「その設定で自己対局 → `.mat` 書き出し →
docker の gnubg で `analyse match`」を回して ER（1 手あたりの損失）を出す。
**docker が要るので `run.mjs` には入れていない。**

| 設定 | 実測 ER | gnubg が付けたラベル（White / Black） | 採否 |
| --- | --- | --- | --- |
| σ=0.30 / cap 0.3 | 75.5 | Awful! / Awful! | |
| σ=0.20 / cap 0.3 | 62.1 | Awful! / Awful! | |
| σ=0.12 / cap 0.4 | 42.9 | Awful! / Awful! | |
| **σ=0.07 / cap 0.5** | **29.2** | Beginner / Beginner | **初心者** |
| **σ=0.04 / cap 0.5** | **20.6** | Casual / Casual | **カジュアル** |
| **0-ply** | **12.8** | Advanced / **Intermediate** | **中級** |
| **2-ply** | **8.3** | **Advanced** / Expert | **上級** |
| **3-ply** | **4.1** | World class / World class | **エキスパート** |

30 局・約 1,700 手ずつ。**3-ply だけ 24 局・1,136 手**（自己対局が重いため）。

> **小さい標本で 1 帯まるごとずれた。** 3-ply を最初 8 局（426 手）で測ったとき
> **5.7 mEMG（Expert）**だったが、24 局で測り直したら **4.1 mEMG（World class）**
> になった。**このくらいの局数では帯をまたぐ**と思っておくこと。

段の名前は gnubg の技量帯から借りた**目安**。「よわい」「つよい」のような
主観語を避けたかったのと、σ を決めた根拠と同じ言葉にしておくと後から追いやすい
ため。

> **ぴったり一致させることは狙っていない。** 0-ply と 2-ply は White と Black で
> 別のラベルが付いており、そもそも境界をまたいでいる。名前が実測とずれても
> 問題にしないこと（**σ を名前に合わせて動かす理由にはならない**）。

**最初に当てで置いた σ=0.16 は ER 50 超（Awful!）だった。** 「Casual くらい
だろう」と置いた σ=0.07 も実際は Beginner で、**勘は 2 つとも外れていた。**
0.12 より下は「読み違えが多い人」ではなく「でたらめ」に見え始めるので採らない。

段ごとに ER が約 1.4 倍ずつ動く、素直なラダーになっている。

> **モデルを差し替えたら測り直すこと。** 今回の発端そのものが「モデルが強く
> なって最弱の段が勝手に格上げされた」ことだった。σ は固定でも、**同じ σ が
> 指す強さはモデルに依存する。**

### ヒント（2026-08-23）

自分の手番に「ヒント」を押すと、**最善手とその見込み**を出す。初心者が
「なぜその手なのか」を確かめられるようにするためのもの。

- **助言の段は対戦相手と無関係に固定**（`ADVICE_LEVEL` = 上級 / 2-ply）。
  初心者と対局していても助言は良いものであってほしいし、**読み違えの乗った
  助言は助言ではない**
- **一度エキスパート（3-ply）にしたが戻した**（2026-08-23）。1 手 1〜3 秒かかって
  待たされ過ぎた。2-ply は実測 14〜53ms で押した瞬間に出る
- **`ADVICE_LEVEL` を 1 行変えるだけで 3-ply に戻せる状態を保つ。** 速い段でも
  **Web Worker 経由**のままにし、計算中はボタンを「考えています…」にして
  二度押しも止める（深い段にしても画面が固まらない）
- **待っている間に局面が動いたら結果を捨てる**（その手番の `legalMoves` と
  `runId` で照合する）。深い段では普通に起きる
- 出すのは**最善手の表記**、**その手を指したあとの見込み**（勝ち / 負けを
  ギャモン・バックギャモンまで分けたもの）、**次点 2 つと最善との差**
- 盤上でも最善手の**移動元に印**を付ける（表記だけだと盤の上で探すのが大変）。
  ただし**色だけに頼っていない**——最善手は必ず表記でも出る
- 候補が 1 つしか残らないときは「ほかの手は大きく劣ります」と言う。
  空欄にするより有用

> **順位と確率で読みの深さが違う。** 順位は `ADVICE_LEVEL`（いまは 2-ply）で
> 付けているが、確率は着手後の局面を 0-ply で評価したもの。探索が equity しか返さないため（確率ベクトルを
> 伝播する探索は engine の `search_vector` にあるが未移植）。
> **「この % を根拠にこの順位」ではない。**

> **手番の最初にしか出さない。** 駒を動かし始めたあとに「1 手番まるごとの最善」を
> 見せても、既に動かしたものと食い違って混乱するだけ。1 手戻せばまた出せる。

ヒントの寿命は**その手番の `legalMoves` 配列に紐づけてある**。局面が動けば別の
配列になるので自動で切れる。消して回る必要がない（消し忘れが起きない）。

#### 段は `plies` ではなく id で作り分ける

**先読み 0 の段が複数ある**ので、`plies` を鍵に Agent を使い回すと
**弱い段が黙って強いまま**になる。Worker が実際にそうなっていた
（`agents` を plies で引いていた）。**しかも Worker が使える環境でだけ起きる。**

Agent を作る入口は `agent.js` の `agentFor(net, levelId)` **1 つだけ**。
アプリ・Worker・テストはここを通す。`tests/backgammon/worker.mjs` が
**全段で**メインスレッドと突き合わせている。

### 推論を速くした 2 つの手当て（2026-08-21）

**1. 第 1 層を疎に回す（3.4 倍・答えは変わらない）**

盤面の符号化 198 次元のうち非ゼロは平均 16.6 個（8.4%）しかない。
1 ポイントあたり 4 ユニットの排他的な符号化なので、空きポイントは
4 ユニットとも 0 になるため。**ゼロを掛けて足しても和は変わらないので、
飛ばしても結果はビット単位で変わらない。** `W1` だけ行優先で持ち直し、
非ゼロの入力ごとに「その行を隠れ層全体へ足し込む」形にした。

> 累算は `Float64Array` で行うこと。`Float32Array` に直接足し込むと
> 1 項ごとに丸められて答えが動く。

**2. 3-ply だけ相手の応手を 2 手に絞る（1.33 倍・近似）**

深い段は期待値の推定に寄与するだけで、1 手の違いが結果に効きにくい。
engine 側で 1,500 局面・3-ply で 2 度測り、**どちらも有意差なし**:

| モデル | 応手 3 → 2 の差 |
| --- | --- |
| 1 層 80 | +0.041 ± 0.271 mEMG |
| **2 層 128→64（同梱）** | **-0.168 ± 0.219 mEMG**（むしろ良い側） |

**engine 側の既定は変えていない。** どの絞り方を使うかはアプリが選ぶ、
という切り分け（`src/agent.js` の `filtersFor`）。

### 思考は Web Worker で走らせる

3-ply は 1 手が秒単位なので、メインスレッドで探索すると画面が固まる
（再描画もクリックも効かない）。`src/worker.js` へ逃がした。

- やり取りは**盤面の JSON と出目だけ**。合法手は Worker 側でも生成する
- 返すのは index と**盤面の鍵**の両方。メイン側で照合し、ずれていたら
  鍵で引き直す
- **出目を見せている間（既定 1 秒）に裏で思考を始める。** 3-ply の思考時間の
  うちその間合いぶんはこれで隠れる。**間合いはスライダーで縮められる**ので、
  隠しきれないときは「長考しています…」を出して待つ
- Worker が作れない環境（`file://` など）ではメインスレッドに落ちる。
  その場合 3-ply では画面が止まるので、起動時のメッセージで断っている

> **`file://` では動かない。** module worker も `fetch` も使えないため、
> ローカルで見るときは HTTP で開くこと（`python3 -m http.server`）。

### ルールエンジンの移植

engine 側の Python が正本。**同じ移植を C# で一度やっており
（`csharp/`）、Python との一致を検証する
パリティテスト（`tests/test_runner.py` と `csharp/tools/export_parity_fixtures.py`）
がある。** JS 移植でも同じ仕組みを使い、**engine が出力する固定局面の
期待値と突き合わせて一致を確認する。**

### 着手 UI と合法手の対応づけ

**`Move.singles` の並びを「操作順」として使ってはいけない。** `generateMoves` は
同じ最終盤面になる手順を 1 つに畳むので、残った並びだけを見ると「順番が違う
だけの合法な手」がクリックできなくなる（初期実装の不具合。全 36 通りのロール中
9 通りで移動元を取りこぼしていた）。

`rules.js` の `nextSingles()` は並びに依存せず、**残りの出目で合法な終了盤面
（`generateMoves` が返した最終盤面の集合）に到達できるか**で次の 1 手を判定する。
最大消費・大きい目優先の規則は `generateMoves` 側で適用済みなので、この判定に
それらを再実装しない。

**「合法な終了盤面と一致した」だけで手番を確定してはいけない。** 途中の盤面が
たまたま別の手順の終了盤面と一致することがある。例えば 4pt と 1pt に 1 枚ずつ・
出目 41 なら、合法手は `4/off 1/off` と `4/3 3/off` の 2 通りで、**`4/off` を
指した直後の盤面は `4/3 3/off` の終了盤面と同じ**になる。一致だけで確定すると、
1 の目が残っているのに手番が終わり、棋譜も `4/3 3/off` として記録される
（実際に起きた不具合）。`app.js` の `turnComplete()` は、終了盤面との一致に加えて
**残りの出目でもう 1 手も指せないこと**（`nextSingles()` が空）を確かめる。

### フォースムーブの自動実行

`auto-force` は**出目を振った直後にだけ**判定する。`legalMoves` はロールで作られ
ターン中は変わらないので、「その長さが 1 か」が「振った時点で手が 1 つしか
なかったか」と同じになる。加えて、まだ 1 つも出目を使っていないこと
（`state.turn.applied` が空）を条件にする。**振った時点でフォースでなかった
ターンでは、片方の出目を使った結果として残りが 1 手に決まっても自動では動かさない。**
片目を使ったら残りも勝手に進んでしまう、という挙動を避けるため。

### 棋譜の書き出し（gnubg / Jellyfish の .mat）

gnubg の読み込み側（`import.c`）は書式に厳しく、**gnubg 自身の書き出しに
合わせる**（`OutputMove` の `"%3d) "` + `"%-27s "`）。実際に踏んだ落とし穴:

- プレイヤー行は `名前 : スコア` の**コロンが必須**。無いと `ImportGame` が
  即 `return 0` して対局がまるごと読み飛ばされる
- 手数の区切りは `1)` の**閉じ括弧**。`strchr(szLine, ')')` で左列の開始を
  探すため、`1:` にすると列の分割がずれて壊れる
- 着手欄は `65: ...`（1〜6 の 2 桁 + コロン + 空白）。ダンスは出目だけ書く
- マネーゲームなので `0 point match` で正しい。`nLength < 0` だけが弾かれ、
  0 は正常値

**マッチまるごと書き出す**（2026-08-22）。ヘッダは ` N point match`
（**アンリミテッドは 0**）で、` Game 1`, ` Game 2`, ... を空行で区切って並べる。
プレイヤー行のスコアは**その局を始めた時点**の値。

- **列の順はファイル全体で固定する。** 局ごとに入れ替えると、プレイヤー行の
  名前と列の対応がずれて**どちらのスコアなのかが壊れる**。どちらを左にするかは
  1 局目の先手で決める
- そのため**先手が右の局は 1 行目の左列が空になる**。以前は「左列が空の行は
  読めない」として避けていたが、**gnubg 自身がその形を書き出す**ことが分かり、
  実物で往復させて問題ないことも確かめた（下記）
- **行は必ず左から右へ埋める。** 空いているからと後のセルを左へ詰めると、
  順序が入れ替わって「先に指したのは誰か」が変わる（実装中に踏んだ）
- **クロフォード局に印は付かない。** gnubg はスコアから導く（うちの判定と
  同じ規則なので、読み直しても食い違わない）

**キューブも書き出す**（2026-08-22）。書式は推測せず、**gnubg 1.07 に自己対局
させて `export match mat` させた出力を写した**:

- セルは `" Doubles => 4"` / `" Takes"` / `" Drops"`。**先頭に空白が 1 つ**入る
  （着手欄には入らない）
- キューブも着手と同じく 1 セルを使う。ダブルした側はテイクされたあと、
  次のセルで改めて振る
- `Wins N points` は**勝った側の列**に置く。その列が埋まっていれば行を足すが、
  **足した行には番号を振らない**
- キューブ行にはコロンが無いので gnubg は「15 桁目以降の二重空白」で列を割る。
  gnubg 自身の書き出しもそうなので、この経路自体は正常（危ないのは
  「左列が空で着手が右列」の組み合わせだけ）

**実物の gnubg で往復させて確かめた。** JS の書き出し → `import mat` →
`export match mat` で、キューブの行は 1 文字も変わらずに戻ってくる
（着手側は `bar/` → `25/`、`/off` → `/0` の正規化と駒の並べ替えが入るが、
意味は同じ）。ドロップで終わった局では最終キューブ値も一致する。

**3 ポイントマッチでも往復させた**（2026-08-22）。ヘッダ・局数・各局の開始時
スコア・キューブの行・`Wins` の位置がすべて保たれ、**先手が右の局の「左列が
空の 1 行目」もそのまま戻ってきた**。
